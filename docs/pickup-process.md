# ピックアップ選考の運用

## 毎回の取得と探索

対象: `sakura-essays/sakurazaka-kosatsu-antenna` の最新 main。既存タスク「坂道ピックアップ更新」の実行日時は日曜19:00（日本時間）を維持する。

1. 作業開始時に full history を持つ最新 main を取得する。既存の未コミット変更は上書きしない。`config/pickups.json`、`config/sources.json`、`config/overrides.json`、`state/articles.json`、`dist/data/articles.json`、`scripts/build.py`、`web/app.js`、`.github/workflows/update.yml` と本書を確認し、最新実装を優先する。
2. `python scripts/pickup_candidates.py --date YYYY-MM-DD --output /tmp/pickup-candidates.json` を実行する。出力先はリポジトリ外。公開一覧・掲載状態・有効著者・ブロック・overrideを照合し、全件のメタデータを探索母集団とする。Git履歴から掲載URLと日時を復元する。履歴が浅ければ取得し直す。取得不能を隠さない。
3. 目標は未評価20〜30候補、うち6〜12本程度の全文精読。候補の約2割（標準6本）は無作為抽出、残りは年代（7日以内、8〜30日、31〜89日、90日以上）、グループ、分類、著者の偏りを緩和する抽出。これは読書機会の配分であり品質推定ではない。候補のタイトル・カテゴリから内容を断定しない。補助的に別候補を追加してよいが件数・方法を記録する。
4. 欅坂は現行データで櫻坂にまとめられる場合がある。タイトル等から欅坂の記事も別途探す。MV・映像も専用分類がない場合はタイトル等で補う。乃木坂・櫻坂・欅坂・日向坂・青葉坂、人物、楽曲・歌詞、映像、ダンス、ライブ、運営、制作者、ファンダム、その他の批評を探索する。分類の欠落は未探索を正当化しない。
5. 登録済み書き手の公開記事、noteの5グループの新着・人気タグも可能な範囲で確認し、見落としを補う。未登録の書き手・未収録記事は候補として報告のみ。sources・RSS・記事掲載状態を勝手に変更しない。初期の候補リストやWeb検索結果だけで選考しない。

## 精読と編集判断

公開本文を最後まで確認できた記事のみ評価する。本文の取得、部分確認、全文精読は別の状態である。有料部分・省略・取得失敗は未評価。タイトルやRSS・過去の紹介文による再採点は禁止。他人の本文を保存した取得物は作業用にとどめ、公開リポジトリに追加しない。

内部で次の配点を用いる: 独自性・発見20、理解・解釈20、観察・論証20、構成・論理15、文体・表現15、読後の問い・批評的価値10。点数だけで選ばない。事実誤認と独自解釈、矛盾と曖昧さ、論証不足と問いを残す構成、単なる感想と固有の観察、完成度と刺激を区別する。重要な根拠に疑義があれば元資料を確認し、確認不能の断定を紹介文へ引き継がない。

スキ数・知名度・交流関係を品質根拠にしない。深山1234も優遇・除外しない。妄ツイ、夢小説、架空の恋愛・会話、転載・要約だけ、宣伝だけ、画像中心、中傷中心、観察の乏しい短感想は対象外。創作も書く人物の独立した批評は公平に扱う。

過去の優秀記事とも比較するが、掲載実績は品質の証拠ではない。直近28日間の掲載記事は継続掲載も含め原則選ばない。例外は、今回精読した具体的な新規候補より推薦価値が高い理由をユーザー向け報告で示す。新規性だけで質を下げない。同一著者への集中を避けるが機械的排除はしない。グループ別の穴埋めをしない。初期16候補を固定母集団にしない。

## 客観的履歴と非公開情報

`state/pickup_discovery.json` に調査状態を累積する。公開可の情報のみ: URL、調査日、取得・精読の成否、再確認の要否、候補抽出日・方法、母集団件数、候補URL一覧。`full_text_obtained` は `full_text_read` と同義ではない。未採用という事実から低品質と推定しない。

点数、順位、主観的評価メモ、不採用理由、詳細な批評、他人の記事本文は公開GitHubへ保存しない。内部採点はその回の作業中だけに保持し、非公開保存先が保証できなければ永続保存しない。公開履歴だけでも、精読済み・未精読・要再調査は次回復元できる。

掲載履歴は `config/pickups.json` のGit履歴を正とする。選考のない週の継続掲載も、直近の設定から判定する。未調査候補は過去runの候補URLから全文精読記録のあるURLを除いて再構成する。取得不能は `recheck_needed: true`。精読済みでも改稿・再評価が必要なら同フラグを付ける。旧作業フォルダの取得記録を移す場合、精読や調査日が証明できなければ不明として扱う。

## 反映・検証・報告

採用は6本。紹介文は原則50〜100字、最大160字。本文に即した具体的な発見を書き、URL・引用・主張・制作意図を作らない。新着と過去を偽らない。

最新mainを再取得し差分を確認する。各URLの実在公開、公開一覧への収録、published、有効著者、保留・除外・削除・ブロックなし、重複なし、紹介文の内容・字数、JSON、ビルド後の6件を確認する。`python -m unittest discover -s tests -v` と `python scripts/build.py --public` を実行する。ビルド生成物や収集データの無関係な差分を手動コミットに混ぜない。

通常の更新対象は `config/pickups.json` と客観的な `state/pickup_discovery.json`。検索・一覧・著者表示・ランダム表示・デザイン・収集・RSSは変更しない。日付入りコミットでmainに反映し、Actionsのテスト・ビルド・Pages公開を確認する。公開サイトの `data.js` の6件が設定と一致し、記事・著者データとフロントエンド上で解決されることを検証する。権限を回避しない。未確認や失敗を成功と報告しない。

毎回日本語で、母集団件数／新規候補件数／全文精読数（新規と既存を区別）／過去掲載以外からの採用数、採用6本の著者・タイトル・URL・具体的な理由・直前との差、例外再選定理由、発掘と未探索範囲、コミット・Actions・公開結果を報告する。「全件メタデータを確認」と「全件精読」を混同しない。
